# Upgrade Guide: 0.70.69 to 0.71.69

This guide moves a consuming project from `@user27828/shared-utils` 0.70.69 to
0.71.69. The release keeps the package native ESM, narrows broad entrypoints,
makes feature integrations opt-in, and makes environment/editor initialization
explicit. Some of these are intentional breaking changes. Migrate only the
features the consuming project uses.

## Instructions for an LLM performing the migration

1. Read the consuming repository's `AGENTS.md` (or equivalent), package
   manifests, lockfile, TypeScript configs, bundler configs, server entrypoints,
   and relevant feature specs before editing.
2. Confirm the project resolves 0.70.69 and identify its package manager and
   package source (registry, Git commit/tag, workspace, or archive). Update the
   dependency reference and lockfile so they resolve the 0.71.69 artifact;
   verify its manifest version instead of assuming a branch or tag name.
   Continue using the consuming project's manager; do not replace the lockfile
   or change package managers.
3. Inventory every shared-utils reference, including value and type imports,
   re-exports, `require()`, dynamic imports, aliases, tests, scripts, generated
   code, and documentation. Search by package name and by `shared-utils`.
4. For each import, identify the symbols actually used. Apply the mappings
   below and use the 0.71.69 package export map and README as the authority for
   public paths. Do not guess paths from source filenames or rewrite imports
   that still resolve and are appropriate for the feature.
5. Install optional peers only for features the project actually imports.
   Preserve feature behavior and initialization order. Do not remove an
   integration merely to avoid installing its peer.
6. Update code and dependency manifests together. Review TypeScript path aliases,
   test mocks, bundler aliases, and code-generation templates that mirror
   package paths.
7. Run the consumer's relevant typecheck, build, lint, and tests after the
   migration. For CommonJS server output, verify the runtime Node version and
   load the actual package entrypoints described below. Fix failures caused by
   stale imports rather than adding broad aliases to old package internals.
8. Summarize changed imports, added peers, initialization changes, commands run,
   and any unresolved use of an unsupported path. Do not commit or publish
   unless the consuming user explicitly asks.

## 1. Migrate utility imports

The package root and `utils` entrypoint now expose dependency-light helpers.
Move configured utilities, singletons, and integrations to their explicit
subpaths.

| Import from 0.70.69                                                                                       | Import in 0.71.69                                                                                              |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `log`, `Log`, or `ORIGINAL_CONSOLE_METHODS` from the root or `utils`                                      | `@user27828/shared-utils/utils/log`                                                                            |
| `OptionsManager` or `optionsManager` from the root or `utils`                                             | `@user27828/shared-utils/utils/options`                                                                        |
| `turnstile` or `Turnstile` from the root or `utils`                                                       | `@user27828/shared-utils/utils/turnstile`                                                                      |
| `formatFileSize`, `sanitizeFilename`, `isValidFilename`, or `convertBytesToUnit` from the root or `utils` | `@user27828/shared-utils/utils/files`                                                                          |
| `formatDate` from the root or `utils`                                                                     | `@user27828/shared-utils/utils/dates`                                                                          |
| Contact CSV/vCard serialization from the root or `utils`                                                  | `@user27828/shared-utils/utils/contact`                                                                        |
| Calendar operations and `CalendarEvent` from `utils/contact`                                              | `@user27828/shared-utils/utils/calendar`                                                                       |
| Meeting-provider data/helpers from the root or `utils`                                                    | `@user27828/shared-utils/utils/meeting-providers`                                                              |
| `detectFormatFromText` from the root or `utils`                                                           | `@user27828/shared-utils/utils/detect-format`                                                                  |
| Environment-specific detection                                                                            | `@user27828/shared-utils/utils/environment` (or the pure `utils` root where its export is already appropriate) |
| JSON merge/storage helpers                                                                                | `@user27828/shared-utils/utils/json` (or the pure `utils` root where its export is already appropriate)        |
| `env` or `getClientUrl` from the `server` root                                                            | Default `env` and named `getClientUrl` from `@user27828/shared-utils/server/env`                               |

The pure root continues to provide `isDev`, `getFileExtension`,
`removeFileExtension`, `isValidEmail`, `normalizeUrl`, `mergeJson`, and
`mergeJsonActions`. Use the focused subpaths for configured or larger
capabilities even when a broader barrel still exposes a compatible API.

Example:

    // Before
    import {
      log,
      optionsManager,
      formatFileSize,
      formatDate,
    } from "@user27828/shared-utils/utils";

    // After
    import log from "@user27828/shared-utils/utils/log";
    import { optionsManager } from "@user27828/shared-utils/utils/options";
    import { formatFileSize } from "@user27828/shared-utils/utils/files";
    import { formatDate } from "@user27828/shared-utils/utils/dates";

### Imports from internal source paths

0.71.69 retains `utils/*` as a legacy compatibility wildcard, but new and
migrated code should use the curated public entrypoints. Replace common deep
imports as follows:

| Legacy path                       | Public path                                                                                              |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `utils/src/functions.js`          | Choose by symbol: `utils/environment`, `utils/validation`, `utils/files`, `utils/dates`, or `utils/json` |
| `utils/src/log.js`                | `utils/log`                                                                                              |
| `utils/src/turnstile.js`          | `utils/turnstile`                                                                                        |
| `utils/src/contact.js`            | `utils/contact`                                                                                          |
| `utils/src/meetingProviders.js`   | `utils/meeting-providers`                                                                                |
| `utils/src/detectFormat/index.js` | `utils/detect-format`                                                                                    |

Preserve the symbol's type/value status. Use `import type` for type-only imports.
For an unlisted deep import, inspect the 0.71.69 `exports` map and declaration
files, then choose the narrowest exported path that contains the symbol. Do not
add a new dependency on an unexported `dist` or `src` path.

## 2. Make initialization explicit

Importing the broad client or server entrypoint no longer initializes globals
or loads environment files.

- If the browser app needs `window.log` and the MUI X telemetry opt-out, import
  `@user27828/shared-utils/client/init` once from its application entrypoint.
  Keep any existing host-provided logger behavior.
- If the server needs the shared logger on `globalThis`, import
  `@user27828/shared-utils/server/init`. The entrypoint initializes it only
  when the host has not already supplied a logger.
- If the server needs shared-utils environment discovery, import `env` and
  `getClientUrl` from `@user27828/shared-utils/server/env`. Importing that path
  performs environment discovery/loading and exports `env` as the computed
  environment object. Replace old imports from the server root; do not treat the
  new default export as a callable initializer. Keep this import ahead of
  modules that read `ENV` options.
- Do not rely on importing `client`, `server`, or `utils` to initialize these
  features as a side effect.

Example server imports:

    import env, { getClientUrl } from "@user27828/shared-utils/server/env";
    import "@user27828/shared-utils/server/init";

If the old application only relied on import-time setup, add the matching
explicit import. Do not add either initializer to a browser-safe or server
entrypoint that does not need it.

## 3. Update WYSIWYG integrations when used

The `client/wysiwyg` entrypoint now provides an engine-neutral switcher and
adapter types. It does not import every editor. Supply adapters for the engines
the application installs.

    import WysiwygEditor from "@user27828/shared-utils/client/wysiwyg";
    import { TinyMceWysiwygAdapter } from "@user27828/shared-utils/client/wysiwyg/tinymce";

    const adapters = { tinymce: TinyMceWysiwygAdapter };

    <WysiwygEditor
      adapters={adapters}
      editor="tinymce"
      value={content}
      onChange={setContent}
    />

For CMS admin UI, pass the selected engine through
`CmsAdminUiConfig.editorAdapters` and pass engine-specific props through
`editorProps`. Without an adapter, CMS body editing uses its textarea fallback.
See [WYSIWYG_SETUP.md](../WYSIWYG_SETUP.md) for complete configuration and
callback examples.

Use only the selected engine entrypoint:

- `client/wysiwyg/tinymce`
- `client/wysiwyg/ckeditor`
- `client/wysiwyg/easymde`
- `client/wysiwyg/mdx`

Use `client/wysiwyg/all` only if the project deliberately installs all four
engines and wants the old all-engine switcher behavior. TinyMCE's default entry
uses a smaller plugin preset; use `client/wysiwyg/tinymce/full` or the
individual TinyMCE feature entries if the app depends on plugins outside that
preset. MDXEditor code-block/language support is opt-in; pass the needed plugins
through its `additionalPlugins` prop.

CMS consumers that configured an editor in the shared admin UI must provide
its adapter in `editorAdapters`, for example:

    import type { CmsAdminUiConfig } from "@user27828/shared-utils/cms/client/ui";
    import { TinyMceWysiwygAdapter } from "@user27828/shared-utils/client/wysiwyg/tinymce/full";

    const cmsConfig = {
      editorPreference: "tinymce",
      editorAdapters: { tinymce: TinyMceWysiwygAdapter },
    } satisfies CmsAdminUiConfig;

## 4. Select narrower client, CMS, and FM entrypoints as needed

The broad client, CMS, FM, and email surfaces remain available where noted in
the package README. These focused paths let a consumer avoid unrelated React,
MUI, editor, provider, and server dependencies. Move an import when its current
path no longer exports the used symbol or when the app needs the narrower
runtime boundary.

- General client hooks/helpers: `client/debounce`, `client/csv`,
  `client/countries`, `client/languages`, `client/timezones`, and `client/dates`.
- Host-supplied country/language data: `client/countries/core`,
  `client/languages/core`, and the corresponding form `custom-data` selectors.
  Supply the empty-code row if the UI needs the empty/other choice. Pass a new
  array identity when supplied data changes.
- CMS client: `cms/client/api`, `cms/client/hooks`, `cms/client/ui`, or the
  public-only `cms/client/public` surface.
- FM client: `fm/client/api`, `fm/client/hooks`, and `fm/client/ui`.
- Email client: `email/client/api`, `email/client/hooks`, and `email/client/ui`.
- Server services: use `cms/server/core` or `fm/server/core` when only the core
  is needed; use `cms/server/express` or `fm/server/express` for router factories.
- Constants-only imports: `cms/constants` and `fm/constants` avoid loading
  schemas. DTO-only imports: use `import type` from `cms/types` or `fm/types`.
  Runtime schemas remain available from `cms/schemas` and `fm/schemas`.

Do not change a broad import solely for style when that feature surface remains
valid and the project benefits from the simpler API. Prefer the focused import
when it removes dependencies the project does not otherwise need.

## 5. Move CMS password and sanitization helpers to server paths

Password and sanitizer helpers are no longer exported from the browser-safe CMS
barrel. Move their imports and install only the peers used by the project:

| Feature                    | 0.71.69 import            | Optional peers                                        |
| -------------------------- | ------------------------- | ----------------------------------------------------- |
| CMS password hash/verify   | `cms/server/password`     | `bcryptjs`                                            |
| HTML/Markdown sanitization | `cms/server/sanitization` | `sanitize-html`; add `marked` when rendering Markdown |

Use `cms/constants` for constant-only imports, `cms/types` for erased types, and
`cms/schemas` when runtime validation is needed. Preserve the existing server
validation and sanitization boundaries; do not move security-sensitive work to
the browser.

## 6. Inject optional storage and service integrations

Only apply these changes when the consuming project uses the integration:

- **FM S3:** local storage remains `createFmStorage(config)`. For S3, import
  `createFmS3Storage` from `fm/server/s3` and pass it as the second argument to
  `createFmStorage(config, createFmS3Storage)`. Install
  `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner` in the consuming app.
- **CMS Redis:** when configuring a Redis URL, import `createCmsRedisClient`
  from `cms/server/redis` and pass it as `redisFactory` to the CMS rate limiter
  configuration. Install `ioredis`. In-memory rate limiting needs no Redis
  package or factory.
- **Other providers:** install peers only for the providers/engines imported by
  the consuming app. Examples include SES SDK, Nodemailer, Express, dotenv,
  papaparse, date-fns, and the selected editor packages. Use the feature table
  in [README Optional Feature Dependencies](../../README.md#optional-feature-dependencies)
  as the version source; do not install every optional peer preemptively.

The root runtime dependencies are `lodash-es`, `nanoid`, and `zod`. UI,
editor, server, storage, mail-provider, and environment integrations are
optional peers and must be direct dependencies of a consuming project when
that project imports them. Update the consuming project's manifest and lockfile
with its existing package manager.

## 7. Use supported CMS/FM contract boundaries

When code currently imports security helpers or schema-heavy values from broad
paths, use the explicit entrypoints described above:

- Password and sanitizer runtime helpers: `cms/server/password` and
  `cms/server/sanitization`.
- Constant values without schema construction: `cms/constants` and
  `fm/constants`.
- Type-only DTO contracts: `import type` from `cms/types` and `fm/types`.
- Runtime validation schemas: `cms/schemas` and `fm/schemas`.
- Domain errors and validation helpers: `cms/errors`, `cms/validation`,
  `fm/errors`, and `fm/validation`.

The constants and DTO types remain based on the canonical schemas/contracts.
Do not duplicate enum tuples or request/response interfaces in the consumer.

## 8. Check CommonJS and Node runtime compatibility

The package remains ESM-only. Every explicit export maps `import` and
`module-sync` to the same ESM file. The package does not provide separate
CommonJS output and intentionally has no `require` or `default` fallback that
would point older Node versions at ESM they cannot synchronously load.

- ESM imports are supported by the package's declared Node engine range.
- Synchronous CommonJS `require()` of package entrypoints requires Node 22.12
  or later and a synchronous ESM dependency graph (no top-level `await`).
- CommonJS applications on Node 22.0 through 22.11 should use dynamic
  `import()` at an async boundary or upgrade their runtime.
- TypeScript projects emitting CommonJS `require()` calls have the same runtime
  requirement even if their source code uses `import` syntax.
- Verify the actual Node version used in production, CI, local scripts, and
  CommonJS test runners. A package-manager engine range alone does not ensure
  that a deployed CJS process meets this requirement.

See the [Node 22.10 release notes](https://nodejs.org/en/blog/release/v22.10.0)
for `module-sync` and the [Node 22.12 release notes](https://nodejs.org/en/blog/release/v22.12.0)
for default `require(esm)` support.

## 9. Verify the migration

After code and manifest updates:

1. Search again for imports from `@user27828/shared-utils` and raw
   `utils/src` paths. Confirm each import resolves through a 0.71.69 public
   export and each symbol still exists.
2. Run the consuming project's TypeScript checks in its real resolution mode
   (for example, NodeNext for Node code and Bundler for Vite/browser code).
3. Build each affected workspace, including server output and browser bundles.
4. Run focused tests for initialization, editor selection, CMS validation and
   sanitization, S3/Redis factories, and any provider whose imports changed.
5. For a CommonJS server, run a fresh Node process using the same runtime as
   production and require the exact shared-utils subpaths it uses. Confirm
   optional feature peers are installed only where those paths require them.
6. Review the diff for behavior changes beyond the required editor adapter and
   explicit integration setup. Update local aliases, mocks, and docs to match
   the final public paths.

The E08 options hot-path optimization changes no public helper signatures or
consumer configuration semantics; it requires no source migration. Geographic
core helpers and custom-data selectors are optional adoption paths, not required
changes to existing bundled country/language selectors.
